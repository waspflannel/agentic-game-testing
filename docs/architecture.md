# Architecture and implementation decisions

See the [implemented interface/test handoff](structured-testing.md). Game-layer source, design and component plans are maintained separately, outside this app-only repository. Structured mode is implemented with code checks and historical bounded startup evidence. The current Codex subscription integration has mocked checks; live sign-in and gameplay acceptance remain pending. The screenshot decision path has been removed; the Electron desktop app is the only interface.

ASHAD uses a Python/FastAPI controller, SQLite WAL metadata, append-only JSONL evidence and a dependency-free HTML/CSS/JS interface rendered only inside the Electron desktop app. This keeps the app local and avoids a database service or frontend build chain. The controller is an owned child of the Electron process, listens only on loopback and accepts only requests carrying the per-launch key Electron injects; HTTP mutations additionally require a same-origin request and an application header. There is no standalone browser mode. Worker HTTP endpoints additionally require per-worker service credentials. Remote placement can use these versioned HTTP contracts with a private authenticated/TLS deployment; no remote infrastructure was provisioned.

Player workers are sibling Docker Linux containers on `ashad-private`. Each owns an Xvfb server, Openbox, a local game action bridge, FFmpeg capture, an official Steam client and persistent private account state. This mechanism gives simultaneous independent controls, rather than switching a shared Windows cursor. The current graphics path is Mesa software rendering; it is an implemented local compatibility choice, not an RTX capacity claim. Resource metrics expose observed CPU/RAM/capture/disk state and leave unavailable GPU data unknown.

The coordinator reserves all planned workers/accounts and the host endpoint before starting a run. SQLite uniqueness constraints enforce leases. Temporary disconnect does not release a reservation. The session cap defaults to one and is configurable. Each player data root belongs to its run; a restored world additionally records its in-game ID. Different runs cannot share world trees or evidence even when their fixtures have identical IDs.

Approved scenario revisions are immutable. A run preserves `approved_plan`; the effective plan can carry logged human goal interventions without erasing approval history. Reruns receive separate scenarios/runs and source-run lineage. Launch and lifecycle command IDs are deduplicated. A run's input epoch and generation prevent a decision from surviving a pause, role/goal intervention or rebind.

Per-run polling tasks can be cancelled before lifecycle control, so a blocked worker read does not hold a global lifecycle lock across all sessions. Heartbeats have an independent loop. Models run independently for each player and receive only their filtered structured game context, explicitly declared messages and allowed static source context. Hidden monitor telemetry never enters player prompts.

`ashad/codex_backend.py` uses the official `openai-codex==0.160.1` SDK and managed ChatGPT OAuth. ASHAD forces ChatGPT authentication and an isolated `<controller-data>/codex` home with OS-keyring storage; the desktop/global CLI home and sign-in are unchanged. API-key authentication and fallback are disabled. Status checks read account and model availability without inference. The default model is `gpt-6-luna`; the selected `plan.model` is frozen in `run.model` at launch and must appear in the connected account's catalog. Gameplay, review and usage records use that run model. Authentication changes share the launch/resume lock; queued runs block login/logout and pending sign-in blocks launch/resume.

Each selection uses a fresh ephemeral Codex thread, a read-only sandbox, deny-all approvals and a JSON schema of permitted choice IDs. Shell, web, app and agent tools are disabled, and instructions prohibit file/tool access. The model selects bounded local candidates; ASHAD validates the returned IDs and executes accepted actions through its worker interface. Planning and review use the same bounded selection contract. Threads are unsubscribed after completion. Timeout/cancellation interrupts the provider turn, and invalid or incomplete output executes no game action. There is no cross-turn provider continuation state or promised latency improvement.

Input is bounded and observation-bound. The worker rejects wrong run/player/epoch, expired observation/action and duplicate action-ID payload conflicts. The game bridge records accepted, running, completed, rejected, cancelled, expired or unknown execution and releases held controls on interruption, lost heartbeat, expiry and teardown. Ambiguous input is never automatically retried. Action/frame clock timestamps and uncertainty accompany records. Current local worker/controller clocks are synchronized by the shared Docker host; remote deployment must retain measured offset uncertainty.

The game remains authoritative. The local exported snapshot merges the pinned DEMO/main trees and adds runtime ENet/Steam/identity/data-path configuration plus read-only diagnostics. UI hosting/joining, character creation, movement, crafting, voting and quest hand-ins stay normal gameplay. Diagnostics only read quest state, connections, world identity, clocks, inventories and machines; they cannot grant items, teleport or complete a quest. The only save transformations happen during explicit offline/prelaunch fresh/restore/conversion setup, with immutable source ZIPs and audit records.

Monitoring separates simulation ticks, telemetry freshness, capture freshness, input acknowledgement, connection/synchronization and shared progress. Quota-vote pauses are not simulation freezes. A player-reported blocker requires evidence of a delivered action and visible prerequisites and remains provisional. Inventory-quantity completion excludes vendor/UI stock by using exact host Inventory/Hotbar paths. Full DEMO completion requires `demo_wrapup_moar` and fresh corroborating observations. Side outcomes, validity and evidence completeness are separate from primary success.

Investigation persists a single deadline before remote IO. Independent controller and worker processes enforce it; the worker's process watchdog reads persistent binding/deadline state and can terminate the game even when its HTTP process is suspended. Capture may continue while bot inputs are held. Report generation occurs after process termination, so evidence work cannot prolong the enforced investigation lifetime.

Ledgers are written and fsynced before their SQLite event index. Startup reconciles an interrupted index write and flags malformed/hash-broken records. Readable reports derive deterministically from retained records. AI review adds separate provisional records, validated against existing evidence IDs. Human decisions and merge history never replace raw events. Whole-run actions remain after rolling media expiry. Storage headroom and run budgets stop admission/measurement visibly rather than silently evicting retained evidence.

Planning/player/review requests record `billing=subscription`, optional returned token counts, latency and provider status. Billed dollar cost remains null for subscription requests. The dashboard separately estimates equivalent API cost using published Standard short-context rates and recorded input/output/cache counts. It groups per-instance totals by run ID and keeps unassigned usage separate; missing usage is not counted as zero. ChatGPT account limits apply; rate-limit failures enter the existing recovery flow. New drafts have no dollar ceiling, and legacy saved dollar caps are ignored for subscription calls with a validation warning. Historical metered usage and pricing remain unchanged. Duration, investigation and storage limits still apply independently.

External validation boundaries are described in [structured testing](structured-testing.md); historical local validation records are not published here. This system does not promise deterministic replay, novice-human behavior, complete bug coverage, fun, a particular completion speed, or successful Steam authentication without licensed accounts.
